# 评估方法

本项目把“工程正确性”“检索质量”和“产品任务效果”分开评估，避免用一套漂亮 demo 代替真实能力证据。

## 1. 工程回归

`tests/` 覆盖确定性规则、状态机、交付门、CLI、打包和对抗性绕过。两套合成 demo 进入 CI：

- `examples/demo-proposal/`：缺料，预期 `SHAREABLE_DRAFT`；
- `examples/demo-proposal-deliverable/`：材料齐备，预期 `DELIVERABLE`。

这些测试回答“相同输入是否稳定执行约定行为”，不回答“真实世界检索是否足够准”。

运行：

```bash
python -m pip install -e ".[test]"
python -m pytest -q
```

## 2. 检索子系统 benchmark

`eval/bench/` 提供候选发现和 rerank 的离线评测脚本。公开结果位于
[`eval/bench/results/`](../eval/bench/results/)，用于记录具体配置下的检索测量。

这些结果只评价检索子系统，不能直接推出：

- 槽级 Evidence Contract 判断准确率；
- writer 的正文质量；
- Claim Audit 的语义判级质量；
- 最终方案的业务可交付性。

第三方数据保留原许可。NFCorpus 的归属与引用、CovidRetrieval 的许可不确定性及公开记录处置见
[THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)。

## 3. 私有任务验收

真实项目材料可能用于本地验收，但材料、逐项标签、转换记录和完整验收报告不进入公开仓库。私有结果
只能帮助维护者发现缺陷，不能作为外部可复核的通用性能声明。

公开发布若需要提出准确率或质量主张，必须提供：

1. 许可允许公开或可由第三方获得的数据；
2. 预先定义的任务、标签规则、成功标准和失败标准；
3. 固定配置、版本与随机性控制；
4. 可重算的逐项输出或足够的聚合数据；
5. 对适用范围和失败案例的说明。

## 4. 当前可支持的结论

当前证据支持：

- 主链在固定契约与合成材料上可复现；
- 缺料、冲突、漏审、陈旧报告和多类缓存字段绕过会被确定性处理；
- 材料齐备与否会导致不同的交付状态；
- 检索组件可以在记录的公开 benchmark 配置下复跑。

当前证据不支持：

- “自动消除幻觉”；
- “适用于所有行业与文档”；
- “无需 auditor 或人工审阅”；
- “已达到生产级准确率”；
- “integrity 等同于不可伪造授权”。

## 5. 新实验的要求

涉及检索、规则阈值或门控行为的改动，应在实现前记录假设、指标、红线和证伪条件；完成后保留配置、
逐项结果与失败分析。稳定的产品决策写入 [DECISIONS.md](DECISIONS.md)，内部原始记录放在被 Git
忽略的私有目录，不把研发过程日志堆进公开文档。
